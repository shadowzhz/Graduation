# Air Hockey 项目交接文档

## 1. 当前阶段

当前项目已完成 Camera 层和第一版 StoneDetector，数据流为：

```text
CameraManager
    -> Frame
    -> StoneDetector
    -> Detection | None
```

当前检测器是基于颜色阈值和轮廓几何约束的单目标检测器。一个帧内可以有多个候选轮廓，但 `detect()` 只返回评分最高的一个候选，找不到目标时返回 `None`。

Camera 层已冻结。后续算法开发不应再把 GUI、Tk 或检测逻辑放回 Camera 层。

## 3. Camera 层接口

### CameraConfig

```python
CameraConfig(
    device=None,
    width=1280,
    height=720,
    requested_fps=200.0,
    pixel_format="MJPG",
    backend="auto",
)
```

`requested_fps` 是请求值，不代表摄像头最终能达到的实际速度。`pixel_format` 是输入源格式，当前 V4L2 显式允许：`MJPG`、`YUYV`、`YUY2`。
`backend` 可设为 `auto`、`gstreamer` 或 `v4l2`，用于自动选择或强制指定摄像头后端。

GStreamer 后端优先使用 Python 原生 `gi.repository.Gst` 直接读取 appsink，避免
`cv2.VideoCapture(..., cv2.CAP_GSTREAMER).read()` 的额外适配开销；如果 Jetson
没有 Python GStreamer 绑定或原生管道启动失败，才回退到 OpenCV GStreamer。

### CameraInfo

Camera 后端打开后返回：

```text
device
backend
width / height
requested_fps
negotiated_fps
source_format
output_format
```

所有后端输出统一为 `numpy.ndarray`，类型和形状必须是：

```text
BGR、uint8、H x W x 3
```

`negotiated_fps` 是驱动或 GStreamer 报告的协商值，不等于真实采集速度。真实采集速度通过 `camera.get_stats().capture_fps`（也可看 `current_fps`）获得。

### CameraManager

```python
from camera import CameraConfig, CameraManager

camera = CameraManager(CameraConfig())
camera.start()

frame = camera.get_latest_frame()  # Frame | None
stats = camera.get_stats()          # CameraStats
info = camera.info                   # CameraInfo | None

camera.stop()
```

`CameraManager` 自动尝试 GStreamer 和 V4L2 后端，并在后台采集线程中只保留最新帧。不要直接操作后端的内部 capture 对象，也不要在 GUI 中读取旧的 `latest_frame` 全局变量。旧的 `GstCameraCapture`、`open_camera`、`open_gstreamer_camera` 兼容层已经删除。

### Frame 和 FrameBuffer

`Frame` 包含：

```text
image       # BGR uint8 HxWx3 ndarray
timestamp   # monotonic 时间戳
sequence    # FrameBuffer 分配的递增序号
```

`FrameBuffer.put()` 可以接收 `Frame` 或直接接收 `numpy.ndarray`。检测逻辑应使用 `Frame.timestamp`，不要自行用墙上时钟替换采集时间。

## 4. Vision 层接口

### ROI

```python
from vision import ROI
roi = ROI(x, y, width, height)
```

ROI 坐标和检测结果坐标都以原始相机图像左上角为原点，单位为像素。检测器内部可以在裁剪后的 ROI 上运算，但返回的中心坐标会自动加回 ROI 偏移。

### Detection

```python
@dataclass(frozen=True)
class Detection:
    center_x: float
    center_y: float
    radius: float
    area: float
    timestamp: float
    circularity: float = 0.0
    score: float = 0.0
```

### StoneDetector

处理流程：

```text
Frame
 -> ROI crop
 -> BGR 转 HSV 或 Lab
 -> inRange threshold
 -> morphology open/close
 -> external contours
 -> area/radius/circularity 约束
 -> circularity + area 评分
 -> 最佳 Detection 或 None
```

典型调用：

```python
from vision import StoneDetector

detector = StoneDetector(
    roi=(350, 650, 580, 650),
    color_space="hsv",
    lower=(170, 100, 80),
    upper=(179, 255, 255),
    min_area=500,
    min_radius=25,
    min_circularity=0.65,
)
detection = detector.detect(frame)
```

当前默认阈值主要针对红色目标。不同摄像头、光照和冰面反光会改变 HSV/Lab 分布，需要通过离线工具先调参。

## 5. 测试工具

### 纯摄像头 FPS 基准

该工具不启动 GUI，也不执行检测和 PNG 编码，用于单独测量 CameraManager 的实际采集速度：

```bash
python3 tools/test_camera.py --benchmark --backend auto --duration 10
python3 tools/test_camera.py --benchmark --backend gstreamer --duration 10
python3 tools/test_camera.py --benchmark --backend v4l2 --duration 10
```

如果 `gstreamer` 和 `v4l2` 都只有约 65 FPS，应继续区分原始 MJPG 读取、硬件解码和
OpenCV 适配层；如果原生 GStreamer appsink 恢复到接近 180 FPS，说明瓶颈确实在
OpenCV 的 GStreamer 读取路径。

Jetson 实测结果（1280x720、MJPG、请求 200 FPS）如下：

```text
原始 MJPG 读取：约 198 FPS
GStreamer 硬件解码 + fakesink：约 182 FPS
旧 OpenCV GStreamer read()：约 65 FPS
原生 GStreamer appsink + CameraManager：约 144 FPS
```

原生 appsink 的关键优化是打开管道时缓存分辨率和通道数，避免每帧调用
`sample.get_caps()`。当前 GStreamer 硬件路径为：

```text
MJPG -> nvv4l2decoder -> nvvidconv -> BGRx -> appsink -> NumPy BGR
```

### 离线图片检测

```bash
python3 tools/test_image.py IMAGE --output OUTPUT
```

完整示例：

```bash
python3 tools/test_image.py \
  tools/4201e120ac50fef54ed9e942ca952e03.jpg \
  --output /tmp/stone_detected.jpg \
  --roi 350 650 580 650 \
  --lower 170 100 80 \
  --upper 179 255 255 \
  --min-area 500 \
  --min-radius 25 \
  --min-circularity 0.65
```

输出图片会叠加 ROI、绿色最小外接圆、红色中心十字、半径和 score。图片路径可以替换为任意 BGR 图像。

### 实时检测 GUI

```bash
python3 tools/test_detection.py
```

红色目标可以从以下参数开始：

```bash
python3 tools/test_detection.py \
  --roi 350 650 580 650 \
  --lower 170 100 80 \
  --upper 179 255 255 \
  --min-area 500 \
  --min-radius 25 \
  --min-circularity 0.65
```

实时工具复用 Tk 界面，左侧显示缩放后的标注画面，右侧显示采集 FPS 和检测结果。检测在原始帧上完成，预览缩放不会改变 `Detection` 坐标。

Jetson 上可加入 `--hardware-preview`，使 GStreamer 使用 `tee` 将解码画面直接交给
`nveglglessink` 渲染到 GUI 的视频区域，从而避开 Tk 和 PNG 编码造成的预览瓶颈：

```bash
python3 tools/test_detection.py --hardware-preview --preview-fps 30
```

硬件预览显示的是未标注的原始画面；检测仍由 Python 按 `--preview-fps` 处理最新帧，
结果显示在右侧面板。硬件预览管道不可用时，工具会自动回退到 Tk 预览。

工具参数：

```text
--roi X Y W H
--color-space hsv|lab
--lower C1 C2 C3
--upper C1 C2 C3
--min-area N
--min-radius N
--min-circularity N
--preview-fps N
--hardware-preview
```

`--preview-fps` 默认是 30，限制检测、标注和 Tk 预览线程的处理频率，避免 GUI
处理拖慢 CameraManager 采集线程。`--hardware-preview` 只适用于 Jetson：GStreamer
通过 `tee` 将一路视频交给 `nveglglessink` 直接嵌入 Tk 视频区域，另一路交给
Python 检测。该模式可以保持接近摄像头的高帧率显示，但硬件显示的是未标注原始画面。

测试命令：

```bash
python3 tools/test_detection.py --preview-fps 30
python3 tools/test_detection.py --hardware-preview --preview-fps 30
```

第一条命令显示 Python/OpenCV 标注，但预览帧率受检测、缩放、PNG 编码和 Tk 显示影响；
第二条命令使用 Jetson 硬件预览，检测中心、半径和 score 显示在右侧面板。

当前实时工具启动时会创建 Tk 窗口并连接摄像头；无可用 DISPLAY 或摄像头时无法完成真实启动验证。启动失败信息会显示在终端和错误对话框中。

## 6. 调参建议

1. 先使用 `tools/test_image.py`，固定一张包含冰壶的图片。
2. 调整 ROI，使其覆盖冰壶可能出现的范围，同时尽量排除无关区域。
3. 调整颜色上下限，确保目标主体连成较完整的区域。
4. 通过 `min_area` 和 `min_radius` 排除噪点。
5. 最后调整 `min_circularity`。过高会漏检被遮挡或反光破坏的轮廓。
6. 再将同一组参数带入 `tools/test_detection.py` 做实时验证。

检测坐标是原始分辨率坐标；如果更换 CameraConfig 的分辨率，需要重新校准 ROI、半径和面积阈值。

## 7. 当前已知限制

- 当前 `StoneDetector` 只返回一个最佳目标，不支持多冰壶结果。
- 评分是启发式评分：`0.8 * circularity + 0.2 * area_score`，不是概率。
- 当前没有 Tracker、Kalman 或 StoneState，连续帧稳定性尚未处理。
- 实时 GUI 的检测和预览默认限制为 30 FPS；硬件预览模式下 Python 只负责检测，原始画面由 Jetson 显示硬件输出。
- `CameraInfo.negotiated_fps` 不能用于判断真实捕获性能，应使用 `CameraStats.capture_fps`。
- GStreamer/V4L2 是否可用取决于本机 OpenCV 编译选项、驱动、设备权限和实际支持的模式。
- 当前 Camera 层统一向 Python 输出 BGR `uint8 HxWx3`，硬件 BGRx 到 CPU NumPy 的复制仍有成本，不能达到摄像头声明的 200 FPS。
- `nvosd` 和 `nvdsosd` 在当前 Jetson 系统中均不可用；因此硬件 `nveglglessink` 预览不能叠加 Python 绘制的圆、十字和文字。
- 项目已移除 `dataclass(slots=True)`，并避免使用 `X | None`、`list[str]` 等语法，以兼容 Jetson 常见的 Python 3.8/3.9。

## 8. 下一阶段建议

建议按以下顺序继续：

```text
Detection | None
 -> Tracker
 -> Kalman filter
 -> StoneState
```

Tracker 应以 `Detection.timestamp` 和中心/半径作为输入，先解决丢帧、短时漏检、目标 ID 和速度估计，再考虑把结果接入 GUI 或控制逻辑。Camera 层保持现有接口不变。

若需要在高帧率硬件画面上显示检测标注，需要安装与 JetPack/L4T 匹配的 DeepStream
并确认 `gst-inspect-1.0 nvdsosd` 可用；当前系统仅安装 `nvidia-l4t-gstreamer`
（35.6.5），没有 `nvosd`/`nvdsosd`，暂不继续安装。

在继续优化前，建议先用以下工具定位性能变化：

```bash
python3 tools/test_gstreamer_transfer.py --mode map --duration 10
python3 tools/test_gstreamer_transfer.py --mode bgrx-copy --duration 10
python3 tools/test_gstreamer_transfer.py --mode bgr-copy --duration 10
```
